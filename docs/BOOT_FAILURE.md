# 0.1.0 启动故障调查

日期：2026-09-23。状态：未解决，暂停分发和安装。

用户报告 OLED，系统版本 `22.5.0 AMS 1.11.2 |E`。安装 0.1.0 后启动 Atmosphère 出现 `std::abort() called (0xffe)`，Program ID 最初抄为 `0100000008`，完整编号尚未取得；同时提示无法保存报告 `00000202`。移除 `atmosphere/contents/4200000054504144` 后恢复开机。该对照说明故障与新增后台加载有关；不能归咎于 Mac，也不能仅凭移除结果区分权限、资源、兼容性或安装文件问题。

源码审查确认：NPDM 未授权 `svcMapMemory (0x04)` 与 `svcUnmapMemory (0x05)`，而固定版本 libnx 的 `nx/source/kernel/thread.c` 在创建、清理线程时使用它们。已补充声明。尚未证明此遗漏就是用户遇到的 boot2 中止原因，也未在真机验证修正。

仍需核查：后台静态 16 MiB 堆在用户常驻模块组合下的启动资源预算；实际固件与 Atmosphère 的加载约束；初始化失败路径。不得把主机结构检查通过写成启动问题已解决。

本次验证：新增对编译后 NPDM 的线程生命周期 SVC 检查，旧产物按预期因权限缺失失败；补充权限后用固定离线工具链重新生成 NPDM/NSP，结构检查通过。打包脚本按预期拒绝生成 0.1.0。没有生成或提供修复安装包，也没有真机修复结论。

保留原始 0.1.0 压缩包用于核对，禁止覆盖为同名“修复版”。打包入口已阻止继续生成 0.1.0，解除阻止需先完成根因调查并变更版本。用户无需重新安装以反复触发崩溃。

## 0.1.1-rc1 手动启动诊断修正版

用户要求在已插入的 SD 卡上清理并更新。此版保留 0.1.0 的发布禁令；新版本补齐线程权限，不生成 boot2.flag，Tesla 显式调用 PM 启动后台并保留返回码，后台记录初始化阶段。它避免再次将该模块加入开机自动加载，但不是原始故障已解决的声明。原始 0.1.0 包保留不覆盖。

## 0.1.1-rc2：修正手动启动按钮的 SM 生命周期

用户在 rc1 点击启动后台后收到 0000E401（InvalidHandle）。源码检查确认 libtesla 仅在 doWithSmSession 回调期间保持 SM 会话；按钮回调直接 pmshellInitialize 时未持有 SM 会话，smGetService 会使用已经关闭的句柄。rc2 在按钮请求期间显式 smInitialize，按初始化成功状态成对释放 PM 与 SM，并分别显示“连接服务管理器”“连接启动服务”“启动后台进程”失败阶段。

这是 rc1 新增手动启动路径中的缺陷，不是对 0.1.0 boot2 原始故障根因的确认。仍无 boot2.flag，仍未在真机验证。

## 0.1.1-rc3：降低静态资源预算

用户报告 rc2 在桌面手动启动返回 00010801（内核 LimitReached）。这表示资源额度已达上限，不单独证明内存是唯一受限项。优先修正本程序偏大的静态预算：固定堆 16 MiB → 4 MiB；RGBA4444 双缓冲由 1280×720 改为 640×360，经 VI 层缩放至屏幕。触摸逻辑坐标、物理控件位置保持不变，绘制边缘精细度降低。

双缓冲分配 983040 字节，线性画布 460800 字节，NV transfer memory 262144 字节，合计约 1.63 MiB；剩余堆供线程、服务及分配器使用。增加半分辨率控件位置、透明区、清空、边界与 tiled offset 测试，发布检查拒绝静态段总量达到 5 MiB 的后台。此修改尚未真机验证，也不能保证解决其他资源种类的额度不足。

## 0.1.1-rc4：据真机日志调整 System 池预算

独立诊断日志 `build/deployment/diag-000000011db6f52a-0.log`：`pm:shell` 初始化成功；`LaunchProgram` 返回 00010801；前后均无 Touchpad PID、命名端口或启动日志。System 池 total=243433472 used=239677440，空余 3756032 字节。rc3 NSO 静态段为 4978700 字节，高于该池剩余 1222668 字节。NPDM `pool_partition=2` 指定 System 池。这足以解释进程创建阶段的失败，仍不排除独立 PM 额度同时不足。

rc4 将静态堆从 4 MiB 减至 2 MiB，RGBA4444 显示由双缓冲改为单缓冲，静态产物上限收紧至 3 MiB，保留手动启动。预计降低启动占用并保留驱动运行时空间；显示绘制需要整帧更新，可能有短暂闪烁。真机启动和输入功能尚未验证，不创建 boot2.flag。

## 0.1.1-rc5：扩大进程启动余量

2026-09-23，Diag 0.2.0 记录极小的 System 池探针成功（LaunchProgram=00000000，PID 138）；同一次诊断稍后启动 Touchpad 仍返回 00010801。A 测试前探针尚在运行。System 池空余 3,645,440 字节，Touchpad rc4 NSO 静态段约 2,881,548 字节，NPDM 主线程栈 64 KiB，名义上只余约 0.67 MiB，且尚未计入进程映射和加载开销。结果强烈支持启动资源余量不足，但物理池统计不等于 PM 资源额度，不能据此断定唯一根因。

rc5 将固定堆从 2 MiB 降到 1.25 MiB、主线程栈从 64 KiB 降到 32 KiB，静态段上限收紧至 2.25 MiB；保留 640×360 单缓冲画面与手动启动。此版应扩大进程加载余量约 0.8 MiB，同时仍需真机验证堆是否足够完成 HID、SD、线程和绘图初始化。若再次失败，应读取新 startup.log（若进程曾进入 main）和 Diag 日志，确认新 NSO SHA 与实际启动返回码。

## rc5 失败后的官方源码复核

用户报告 rc5 仍返回 00010801。此前依靠物理池剩余量作缩堆判断不充分，并混用了十进制字节数与 MiB；此处“2.88 MiB/3.64 MiB”等近似表述应以 [内存需求核查](MEMORY_RESEARCH.md) 中的字节数及重新换算为准。官方源码确认存在可读取 System 资源组真实额度的 pm:dmnt 65001 接口，Diag 0.2.0 漏用了它；同时 libnx 显示缓冲和 NV 传输内存也来自堆，rc5 1.25 MiB 堆缺乏运行余量。先补齐资源组测量与预算，不再凭物理空余继续缩堆。

## 2026-09-24：rc6 Applet 试验

rc5 再次收到相同启动错误反馈。按用户同意的方案，rc6 将 NPDM 的物理池与 PM 资源组同时切至 Applet，恢复 4 MiB 堆和 64 KiB 主线程栈，不创建开机标记。Diag 0.3.0 记录两个组的真实配额；旧极小探针继续留在 System，不能把它成功当作 rc6 的验证。见 [首测步骤](APPLET_RC6.md)。本次改变内存来源，不认定所有 00010801 均由内存导致，原始 fatal 根因仍未确认。
